Spec format

A spec is a Markdown file with a YAML frontmatter block that gives it an id and a type. Specs link to each other through frontmatter fields, and the links form a graph that the agent and the Specs tool read. This page defines the format. For why specs exist and how the agent uses them, read Living specs.

What makes a file a spec

Section titled “What makes a file a spec”

A file is a spec when all of these hold:

  • Its name ends in .md. Any .md file under the project root qualifies; the name SPEC.md is a convention, not a requirement.
  • It starts with a frontmatter block: a line containing only ---, YAML, and a second line containing only ---. A leading byte order mark and Windows line endings are accepted.
  • The frontmatter parses as YAML and has a non-empty id and a non-empty type.

A Markdown file without both fields, with malformed YAML, or without frontmatter is not a spec and is ignored. No other check applies: a file does not need a title to be indexed, although spec_create requires one and the bundled spec-graph skill treats it as required.

Frontmatter fields

Section titled “Frontmatter fields”
FieldTypeRequiredDescription
idstringyesUnique slug that names the spec. Other specs link to it by this value. It cannot be renamed with spec_update.
typestringyesWhat kind of spec this is. See Types.
titlestringno, but expectedHuman-readable title. The Specs tool shows the id when it is missing. spec_create requires it.
statusstringnoLifecycle state. See Statuses.
parentstringnoOne spec id. The tree edge; mirrors the code hierarchy.
depends-onlist of stringsnoSpec ids this spec depends on.
referenceslist of stringsnoSpec ids this spec cites without depending on.
implementslist of stringsnoSpec ids this spec implements.
coverslist of stringsnoFree-form coverage ids or topics. Not links; they are not resolved.
tagslist of stringsnoFree-form tags. Filterable with spec_grep.

spec_create writes new frontmatter in this order: id, type, status, title, parent, depends-on, references, implements, covers, tags. spec_update keeps the order a file already has. Tools write lists inline, as [a, b]; block-style YAML lists are read normally. Unknown extra fields are allowed and preserved.

Types

Section titled “Types”

The type value is a free string in the read model: the graph indexes whatever is on disk. The authoring tools (spec_create) accept five values:

typeUsed forScaffold headings from spec_create
goal-and-requirementsThe product goal and scope; the root of the graph.Goal, Scope
architecture-designSystem-wide topology, cross-cutting decisions, and invariants.Drivers, Decisions, Invariants, Out of scope
module-designA package or module: its responsibility and boundary.Responsibility, Boundary
submodule-designThe same, for a directory-level module inside a package.Responsibility, Boundary
task-specA temporary working document for one piece of work. Not durable; deleted when the work lands.Purpose, Open items

A spec of any other type still appears in the graph. The Specs tool labels it with an uppercase tag derived from its type.

Statuses

Section titled “Statuses”

status is optional and tracks a spec’s lifecycle. spec_create accepts these values:

statusMeaning
draftBeing written; not yet reviewed. Workflows create specs as draft.
activeIn force.
staleDrifting from the code.
doneFinished; used mainly by task-specs.
deprecatedNo longer in force.

The usual path is draft to active, then stale, done, or deprecated. spec_update does not check status or type values against these lists, so a typo is stored as written.

File placement

Section titled “File placement”
FileLocationType
Product goalgoal-and-requirements.md at the project rootgoal-and-requirements
Architecturearchitecture.md at the project rootarchitecture-design
Module specSPEC.md beside the module’s code, for example packages/server/SPEC.mdmodule-design
Sub-module specSPEC.md beside a meaningful directory inside a modulesubmodule-design
Task-spec.thinkrail/context/TASK-<slug>.md in the workspacetask-spec

The layout is fractal: a package and its sub-directories each have a SPEC.md. Task-specs live in the workspace’s gitignored .thinkrail/context/ folder. Existing design documents can join the graph in place by gaining frontmatter, with no change to their content.

How the graph is built

Section titled “How the graph is built”

Every spec is a node keyed by its id. Four frontmatter fields create edges from the spec that declares them to the spec they name:

FieldEdgeShapeTypical use
parenttree edgeone idA module’s spec points at its package’s spec, which points at architecture, which points at the goal.
depends-ondependencylistThe module may rely on the target; mirrors an allowed import or contract.
referencesreferencelistThe spec cites the target without depending on it.
implementsimplementationlistThe spec describes an implementation of the target.

parent edges form the hierarchy. The other three form a dependency layer across that tree. Each edge also gets a derived reverse edge, so spec_get can report which specs point at a given spec. The tools do not treat the three list fields differently from one another; the distinction is for readers and for the filters on spec_grep and spec_graph.

flowchart TD
    Goal["goal-and-requirements"] --> Arch["architecture"]
    Arch --> Server["module-server"]
    Arch --> Web["module-web"]
    Web -.->|depends-on| Contracts["module-contracts"]
    Arch --> Contracts

covers and tags are metadata, not edges.

Duplicate ids and broken links

Section titled “Duplicate ids and broken links”
  • If two files declare the same id, the file that sorts first by path wins the node and the other is reported as a duplicate. Files are visited in name order, comparing Unicode-normalized names, so the winner is the same on every filesystem.
  • A link whose target id does not exist stays in the graph as a missing target; it does not stop the other specs from loading.
  • spec_validate reports dangling links in all four link fields, duplicate ids, and cycles in the parent chain. It does not check cycles in depends-on, references, or implements.

[[wikilinks]]

Section titled “[[wikilinks]]”

ThinkRail’s own specs cite other specs in prose as [[spec-id]]. That is a writing convention for human readers and agents. No tool parses or resolves it, and the Specs tool renders it as plain text. The only links in the graph are the frontmatter fields above.

Spec tooling limits

Section titled “Spec tooling limits”
  • Which files are scanned. The scan starts at the workspace root and skips directories named node_modules, .git, dist, build, .claude, .superpowers, .gsd, .mockups, and .playwright-mcp. The last five hold other assistants’ scratch files that can carry spec-shaped frontmatter. Symbolic links are never followed. Only files ending in lowercase .md are read.
  • spec_create path rules. The path must be relative to the project root, end in .md, stay inside the root, avoid the skipped directories, and pass through no symbolic link. Windows drive letters and stream syntax (a colon in the path) are refused. Names that differ only by case or Unicode form are resolved to the spelling already on disk, and ambiguous matches are refused. The call fails if the file or the id already exists.
  • Read model. The graph reads frontmatter values as strings or lists of strings. Numbers and booleans become strings, empty values are dropped, nested maps are ignored for the graph, and a single string where a list is expected is read as a one-item list.
  • Write model. spec_update rewrites only the frontmatter block, in the line ending the block already used, and keeps comments, field order, and unknown or nested fields. It cannot edit prose, rename an id, remove id or type, or turn a file into a non-spec. There is no tool to move or rename a spec file.
  • Search. spec_grep matches one line at a time, as a substring or a JavaScript regular expression, across spec files only, and returns at most 200 matches by default. There is no semantic or embedding search.
  • Freshness. Each call checks file modification time and size, so edits from any source are picked up on the next call. An edit that keeps both the same size and the same timestamp tick would be missed.
  • One graph per workspace. The index is built from the workspace root. Another workspace on a different branch has its own graph.
  • Read-only viewer. The Specs tool shows the parent hierarchy as a tree, sorted by title within each level. There is no spec editor in the app; specs change through the agent, your editor, or the terminal.
