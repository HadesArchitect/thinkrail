MCP configuration

ThinkRail connects to Model Context Protocol servers through the MCP support built into pi. pi owns the connections, OAuth, and tool exposure; ThinkRail adds a management page, approvals for servers that a repository defines, and a confirmation prompt for calls that may change data. This page covers the configuration files and the behavior around them. For the task-oriented guide, read Connect MCP servers.

Note

ThinkRail has no pi executable, so the pi mcp add and pi mcp login shell commands from the pi documentation are not available. Use Settings → MCP servers, edit the files below, or use /mcp in a chat.

Configuration files

Section titled “Configuration files”
ScopeFileApplies toLoaded when
Usermcp.json in the pi agent directory, by default ~/.pi/agent/mcp.json (set PI_CODING_AGENT_DIR to move it)Every project on this hostAlways
Project.pi/mcp.json in the workspaceChats in that projectThe project is trusted, and each entry is approved

Keep personal servers and servers that need credentials in the user file. Use the project file for servers the repository needs, since it is committed with the code.

A project entry with the same name as a user entry replaces it. A project entry with none of command, url, or type is an override: it can set only enabled, exposure, and toolExposure on the user-level server of the same name and keeps everything else, including env, headers, and auth.

A changed file reaches a running chat at its next idle reload; a busy chat waits until it is idle. Invalid entries are reported and skipped without stopping other servers from loading. Settings shows an unreadable file or a file without a valid mcpServers object as a file-level error.

File format

Section titled “File format”

The file is a JSON object with a mcpServers object that maps server names to entries.

Server names may contain only letters, digits, _, and -. Names that differ only in - versus _ count as the same server, and a second one is rejected. A server’s tools are named mcp__<server>__<tool>.

Entry fields

Section titled “Entry fields”

An entry is a stdio server (it has command) or a streamable HTTP server (it has url). The legacy sse transport is rejected.

FieldTypeApplies toDescription
commandstringstdioOne executable, not a shell string. A leading ~/ means your home directory.
argsstring[]stdioArguments, one per element. Never split by a shell.
envobject (string values)stdioEnvironment variables for the process.
cwdstringstdioWorking directory. A relative path resolves against the chat’s directory.
urlstringHTTPThe server’s streamable HTTP endpoint; http: or https:.
headersobject (string values)HTTPRequest headers.
oauthobjectHTTPOAuth client settings; see OAuth.
authobjectHTTP{ "provider": "<name>" }, using a pi provider’s credentials. Allowed only in the user file, and only for https URLs or loopback addresses.
typestringbothOptional. stdio, http, or streamable-http. command or url selects the transport when it is omitted.
timeoutnumberbothPer-request timeout in seconds. Positive. Default: 60.
enabledbooleanbothfalse keeps the entry without connecting.
exposurestringbothHow tools reach the model; see Tool exposure.
toolExposureobjectbothPer-tool exposure. Keys are tool names or patterns where * matches any characters.
descriptionstringbothOne sentence about what the server offers. It lists the server for the model and for tool search.

env and headers values can reference environment variables as ${NAME}. A value can also be a command that produces the value, written as a ! prefix that makes up the whole value:

Commands run on the host. Prefer ${NAME} references over literal secrets; Settings warns when a value looks like a secret.

Tool exposure

Section titled “Tool exposure”

exposure decides how the model reaches a server’s tools.

ValueBehavior
deferredThe default in ThinkRail. Tools are not declared up front; the agent loads them through tool_search when it needs them.
directTools are declared to the model up front, like built-in tools. Best for small, frequently used servers.
hiddenTools are registered but unreachable.

codemode and codemode-deferred are valid values in the file format, but ThinkRail does not ship the codemode runtime and treats them, and an unset value, as deferred. toolExposure overrides the server’s value for individual tools; an exact tool name beats a pattern, and among patterns the first match wins.

OAuth

Section titled “OAuth”

HTTP servers that use OAuth need no credentials in the file. When a server rejects an unauthenticated connection, its row shows Needs sign-in. Servers that support dynamic client registration need nothing else; for others, configure a registered client in oauth:

FieldTypeDescription
clientIdstringRegistered client id.
clientSecretstringOptional secret. May use ${NAME} or a !command.
callbackPortintegerLoopback port, 1 to 65535. The redirect URI is http://127.0.0.1:<port>/callback.
callbackUrlstringRedirect URI. Must be http on localhost, 127.0.0.1, or [::1], with no query or fragment.
scopestringSpace-separated scopes, for servers that do not advertise theirs.
clientNamestringName to register under, for servers that accept only known clients.
clientRegistrationdcr | cimdcimd identifies pi by a client metadata document instead of registering. It cannot be combined with clientId or clientName.
authServerMetadataUrlstringMetadata document of the right authorization server, when the server advertises the wrong one. https, or http on a loopback address.

A running chat uses new credentials on its next turn. pi stores tokens, not ThinkRail:

FilePurpose
~/.pi/agent/mcp-auth.jsonOAuth tokens (inside the pi agent directory).
~/.pi/agent/mcp.logMessages that servers send, one entry per message. Moves to mcp.log.1 after 5 MB.

Credentials belong to a server name and URL. Servers with the same URL under different names sign in separately.

Presets

Section titled “Presets”

Settings → MCP servers lists presets in its empty state and in the Presets section of the Add a server dialog. A preset prefills the form and still goes through the confirmation step.

PresetEndpointExposureNotes
Context7https://mcp.context7.com/mcpdirectCurrent library and framework documentation. No sign-in.
DeepWikihttps://mcp.deepwiki.com/mcpdirectQuestions about public GitHub repositories. No sign-in.
Linear (read-only)https://mcp.linear.app/mcp/readonlydefaultRead-only endpoint. Sign in after adding.
Sentryhttps://mcp.sentry.dev/mcpdefaultIssues, events, and releases. Sign in after adding. Flagged as able to modify data.
Playwrightnpx -y @playwright/mcp@0.0.83defaultDrives a browser on the host. Added disabled; you turn it on per project. Flagged as able to modify the sites its browser opens.

All presets are added at user scope. The same dialog has a GitHub recipe under Paste JSON (labeled “Not a preset”): the read-only GitHub endpoint with an Authorization header built from your GitHub CLI token, which needs gh signed in on the host.

Managing servers in Settings

Section titled “Managing servers in Settings”

Settings → MCP servers needs an open workspace. Each row shows the server name, a scope tag (User or Project), the transport (stdio or HTTP), an exposure menu, a status, an on/off switch, and a menu with the actions available for its state.

Status labels: Starting, Connected, Needs sign-in, Failed, Disconnected, Disabled, Disabled in this project, Disabled in this chat, Pending approval, Invalid config, Pending reload, Not running, Handled elsewhere, and Unknown. Actions that can appear include Sign in, Review & approve, Edit, Test connection, Reconnect, Reload now, Open a chat, Show log, Share with repo, and Remove.

  • Add a server and Import mcpServers JSON open the Add MCP servers dialog with Form and Paste JSON tabs. Choose scope User — all projects or Project — .pi/mcp.json. A server that runs a command or carries secrets goes through a Confirm what will run step before it is saved.
  • Share with repo writes a project override entry for a user-level server so that the repository can record its enabled state or exposure.
  • Show log shows the latest 200 lines of that server’s messages from mcp.log, with credential-looking values masked.
  • Secret-looking values and endpoint credentials are masked in the page, in logs, and in error text.
  • Writes keep unknown keys and indentation and replace the file atomically. The host refuses to write a project file when .pi or mcp.json is a symbolic link, with error MCP_PATH_UNSAFE. An invalid config is refused with MCP_CONFIG_INVALID.
  • If another extension has taken over /mcp, or pi settings contain -builtin:mcp, management in Settings is read-only and the code is MCP_HANDLED_ELSEWHERE.

In a chat, Resources lists MCP servers with Enable in this chat and Disable in this chat, which restart that chat’s servers when it is idle, and Sign in. Chat-level choices are not saved.

Repository-defined servers and approval

Section titled “Repository-defined servers and approval”

A server in the project’s .pi/mcp.json can run commands on your machine, so two separate consents gate it:

  1. Project trust. The project must be trusted at the pi-resource level. See Trust a project and Trust model.
  2. Per-entry approval. Even in a trusted project, each repository entry stays Pending approval until you choose Review & approve and confirm what it will run: where it connects, its working directory, and the names of its environment variables.

Approval is stored per project in projects.json in the ThinkRail data directory (~/.thinkrail, or THINKRAIL_DATA_DIR) under mcpApprovals, which maps each server name to a SHA-256 fingerprint of the whole entry as written. If the entry changes in any way, including a reordering of toolExposure, its fingerprint no longer matches, the row shows Changed since approval, and the server stops loading until you approve it again. Repository override entries are approved the same way. Per-project switches for user-level servers are kept in mcpOverrides in the same file and are not part of the repository.

User-level servers are not gated by trust or approval.

Call confirmation

Section titled “Call confirmation”

Before any mcp__<server>__<tool> call, ThinkRail checks the tool’s readOnlyHint annotation. A tool that declares readOnlyHint: true runs without asking. For any other MCP tool, the chat shows “Allow the MCP call <server>/<tool>? It may change data.” with a preview of the arguments (first 160 characters) and three answers:

AnswerEffect
DenyThe call is blocked and the agent is told you denied it.
Allow onceThe call runs.
Allow in this chatThe call runs, and later calls to the same tool in this chat run without asking. The grant is not saved and ends with the chat.

Note

Builds after 0.2.0-nightly.33 ask in the chat next to the tool call and add an Always allow answer that remembers the approval (#749). This page describes the behavior up to 0.2.0-nightly.33.

Dismissing the prompt, stopping the run, or having no interface attached blocks the call. Sending a steer message cancels any confirmations that are waiting. The prompt covers MCP tools only; the tool search and resource tools are not named mcp__..., and pi marks the resource tools read-only.

Subagents cannot call MCP tools at all. The parent calls them and passes the results in the task text.

Sign-in

Section titled “Sign-in”

Sign in on a row, /mcp login <name> in a chat, and the same in the chat’s server list all start an OAuth flow. Settings returns the authorization URL to your browser; a chat never opens a browser on the host. If your browser runs on a different machine from the host, paste the redirected URL back into the sign-in screen. A per-server lock allows one sign-in at a time and reports “A sign-in for <name> is already running in Settings” (or “in a chat”) otherwise. Sign out deletes the stored credentials.
