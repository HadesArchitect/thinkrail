Reference

Tools the agent can call

ThinkRail runs pi in-process and adds a fixed set of tools to every chat on top of the tools pi ships. This page lists those additions: name, purpose, parameters, and notes. For how the pieces fit together, read ThinkRail and pi.

What is and is not listed here

Section titled “What is and is not listed here”

pi owns its built-in tools (read, bash, edit, write, grep, find, ls, and the rest) and its MCP tools. They are not documented on this page; see the pi documentation. Tools from MCP servers are named mcp__<server>__<tool> and are covered in MCP configuration.

Parameter types follow the tool schemas the model sees. A parameter marked Required: no may be omitted.

GroupToolsProvided byAvailability
Spec graphspec_grep, spec_get, spec_graph, spec_create, spec_update, spec_delete, spec_validatepi-spec-graphAlways on
TODO plantodo_list, todo_add, todo_update, todo_promote, todo_remove, todo_write, todo_plan_summarypi-todosAlways on
SubagentsAgent, get_subagent_resultpi-subagentsOn unless subagents are turned off
Background commandsbackground_commandpi-background-commandsAlways on
Host toolsask_user_question, set_title, resolve_comment, request_reviewThinkRail hostrequest_review is opt-in; the rest are always on
Web researchweb_search, fetch_content, get_search_contentpi-web-accessAlways on
VisualizevisualizeThinkRail extensionOn unless turned off in Settings → Extensions

Note

ThinkRail adds no confirmation prompt to the tools on this page. The only calls it gates are MCP tool calls that do not declare readOnlyHint; see MCP configuration. pi’s own tools, including bash, do not ask first either. See What the agent can do without asking.

Spec graph tools

Section titled “Spec graph tools”

Provided by the pi-spec-graph package. The tools read and manage the project’s spec graph. An always-on system prompt rule tells the agent to consult the owning spec when work touches a documented boundary, contract, invariant, behavior, or architecture decision. The tools manage frontmatter and structure only; the agent edits spec prose with pi’s write and edit.

The index is refreshed from disk on every call (changed files are re-read), so specs changed by hand or by another tool are always current. Paths are relative to the working directory of the chat (the workspace root).

spec_grep

Section titled “spec_grep”

Search the text of spec files, optionally narrowed by metadata. Returns path:line: snippet matches.

ParameterTypeRequiredDescription
patternstringyesSubstring, or a regular expression when regex is true.
regexbooleannoTreat pattern as a regular expression. Default: substring.
ignoreCasebooleannoCase-insensitive match. Default: true.
typestringnoOnly search specs whose type equals this value.
tagstringnoOnly search specs that carry this tag.
parentstringnoOnly search specs whose parent is this id.
dependsOnstringnoOnly search specs whose depends-on list contains this id.
limitnumbernoMaximum matches to return. Default: 200.

An invalid regular expression returns an error result. Matching is per line; there is no semantic search.

spec_get

Section titled “spec_get”

Look up one spec by id. Returns its frontmatter, file path, resolved forward links, and reverse links (specs that point at it) across parent, depends-on, references, and implements. A link whose target does not exist is marked (missing). The result has no prose body; read the body with read using the returned path.

ParameterTypeRequiredDescription
idstringyesThe spec id to look up.

spec_graph

Section titled “spec_graph”

Return a bounded slice of the graph around one spec.

ParameterTypeRequiredDescription
rootstringyesId of the spec to start from.
directionsubtree | ancestors | neighborsyessubtree walks down the parent tree, ancestors walks up to the root, neighbors crosses one edge kind and its reverse.
depthnumbernoHow many hops to expand. Default: 1.
edgeparent | depends-on | references | implementsnoFor neighbors only: which edge kind to cross. Default: depends-on.

spec_create

Section titled “spec_create”

Create a spec file with scaffolded frontmatter and a heading-only body chosen by type. The scaffold headings are Responsibility and Boundary for module and submodule specs; Drivers, Decisions, Invariants, and Out of scope for architecture specs; Goal and Scope for goal specs; Purpose and Open items for task-specs.

ParameterTypeRequiredDescription
pathstringyesPath relative to the project root, ending in .md (for example src/foo/SPEC.md).
idstringyesUnique spec id.
typeenumyesgoal-and-requirements, architecture-design, module-design, submodule-design, or task-spec.
titlestringyesHuman-readable title.
statusenumnodraft, active, stale, done, or deprecated.
parentstringnoId of the parent spec.
dependsOnstring[]noIds for the depends-on list.
referencesstring[]noIds for the references list.
implementsstring[]noIds for the implements list.
coversstring[]noFree-form coverage ids.
tagsstring[]noTags.

The call fails if the file exists, the id is already in use, or the path cannot be indexed. See Spec tooling limits for the path rules.

spec_update

Section titled “spec_update”

Edit a spec’s frontmatter in place. Existing field order, comments, nested fields, and line endings are kept; the body is never touched. The id cannot be renamed and id and type cannot be removed.

ParameterTypeRequiredDescription
idstringyesId of the spec to update.
setobject (string values)noScalar fields to set or overwrite, such as title, status, or parent. List fields are rejected here.
removestring[]noFrontmatter field names to delete.
addListobjectnoEntries to add to list fields. Keys: depends-on, references, implements, covers, tags; each value is a string array. Duplicates are not added.
removeListobjectnoEntries to remove from the same list fields. A list left empty is deleted.

spec_delete

Section titled “spec_delete”

Delete a spec file by id. Other specs that link to it are not edited; run spec_validate afterward.

ParameterTypeRequiredDescription
idstringyesId of the spec to delete.

spec_validate

Section titled “spec_validate”

Report structural problems in the graph: links whose target does not exist (for parent, depends-on, references, and implements), duplicate ids, and cycles in the parent chain. Takes no parameters.

TODO plan tools

Section titled “TODO plan tools”

Provided by the pi-todos package. The tools read and write the chat’s shared plan, which you see in the TODO List rail and on the plan page. The plan is stored per chat at .thinkrail/context/todos/<chat id>.json inside the workspace, in the gitignored .thinkrail/context/ folder, so it is scratch state and not committed.

A plan has groups (one task, titled by outcome) that contain ordered steps, plus a loose queue at the end for raw items that either side can add. A step is pending, in_progress, or done. Exactly one step is in_progress: setting a step to in_progress returns any other to pending and the result says it was paused. A group’s status is derived from its steps and never stored. Most results end with a short reminder line, such as “nothing is in_progress” or a prompt to write the plan summary once every item is done.

An always-on rule tells the agent the list exists, that a pending loose item is promoted into its own group when the agent takes it into work, and that a plan is created when you ask for one or the work needs at least three substantive steps.

todo_list

Section titled “todo_list”

Read the plan. The agent re-reads it before choosing each next step because you can edit it at any time.

ParameterTypeRequiredDescription
statuspending | in_progress | donenoReturn only items with this status. Omit for the whole plan.

todo_add

Section titled “todo_add”

Add one item without touching the rest of the plan.

ParameterTypeRequiredDescription
titlestringyesOne-line step title: imperative and about the outcome.
groupstringnoTitle of the group to append to. The group is created if it does not exist.
afterstringnoId of an existing step to insert after. Overrides group. Must be a step inside a group; an id of a loose item is rejected.
notestringnoShort secondary line for agent-facing detail.

With neither group nor after, the item goes into the loose queue.

todo_update

Section titled “todo_update”

Change one item. This is how the agent marks progress.

ParameterTypeRequiredDescription
idstringyesId of the item.
statuspending | in_progress | donenoNew status. Done items stay in the plan as history.
titlestringnoNew title.
notestringnoNew note. An empty string clears it.
summarystringnoCompletion summary in Markdown, set together with status done. An empty string clears it.
verificationstringnoChecks that were run, each as check → result, or not verified. An empty string clears it.
commitSubjectstringnoOne-line commit subject for the step’s code changes, set together with status done. An empty string clears it.

When a step with changes goes to done, the host commits that step’s delta under commitSubject, falling back to the step title. The host only commits when its safety conditions hold (a recorded baseline, no unrelated changes already in the tree, an unshared window, and a non-empty delta); otherwise it skips the commit. Marking the last open item done prompts the agent to call todo_plan_summary.

todo_promote

Section titled “todo_promote”

Turn a loose item into a group of its own in one step. The group keeps the loose item’s id and title unless title is given.

ParameterTypeRequiredDescription
idstringyesId of a loose item. A step that is already inside a group is rejected.
titlestringnoTitle for the new group instead of the loose item’s own.

The call fails when the id is unknown, the resolved title is empty, or a group with that title already exists.

todo_remove

Section titled “todo_remove”

Delete an item by id. The agent uses it only when you ask to drop an item, because finished items are marked done rather than removed.

ParameterTypeRequiredDescription
idstringyesId of the item to remove.

todo_write

Section titled “todo_write”

Lay out or reconcile the plan from groups. Steps are matched to existing steps by group title plus step title and keep their status, summary, and id, so repeating the call is safe. A status passed for an existing step is ignored. Steps the agent leaves out are dropped, but loose items and done items are always kept.

ParameterTypeRequiredDescription
groupsarrayyesThe plan as tasks.
groups[].titlestringyesTask name, an outcome.
groups[].todosarrayyesThe task’s ordered steps.
groups[].todos[].titlestringyesStep title.
groups[].todos[].statuspending | in_progress | donenoInitial status of a new step. Default: pending.
groups[].todos[].notestringnoShort secondary line.

todo_plan_summary

Section titled “todo_plan_summary”

Set the plan-level completion summary after the last item is done. The summary is cumulative across the whole plan and shaped like a pull request body, with ## Summary, ## Changes, and ## Testing sections. The host prepends it when it renders the PR body for Open PR.

ParameterTypeRequiredDescription
summarystringyesThe cumulative summary. An empty string clears it.

If items are still open, the summary is saved but only shows once everything is done.

Subagent tools

Section titled “Subagent tools”

Provided by the pi-subagents package, on top of pi-delegation. A subagent is a hidden child pi session with its own context window. It works in the parent’s workspace and branch, runs without anyone to answer questions, and returns one final report. See Delegate to subagents for the workflow.

Agent

Section titled “Agent”

Run a task in a subagent. Several Agent calls in one assistant message run in parallel.

ParameterTypeRequiredDescription
subagent_typestringyesName of the agent definition to run, such as scout.
taskstringyesThe complete, self-contained task. The subagent sees only this text.
modelstringnoA model for an unpinned agent, preferably provider/id.
run_in_backgroundbooleannoDo not wait. The call returns the child session id at once.

Behavior and limits:

  • Foreground (default). The call waits and returns the subagent’s final report. A failed run raises a tool error that still carries the run’s details.
  • Background. The result is the child session id. When the run finishes, a subagent-completion message is delivered to the chat as a follow-up and starts a new turn, unless you stopped the subagent yourself. get_subagent_result fetches the result on demand.
  • Model. A definition’s model wins over the model parameter, which wins over the parent chat’s model. A reference matches provider/id exactly, an exact id, or a unique id prefix; an ambiguous or unknown reference is an error.
  • Result size. Reports are capped at 50,000 characters; the full text stays in the child transcript.
  • No recursion, no MCP. Subagents cannot call Agent or get_subagent_result, and they cannot call MCP tools. The parent calls MCP tools itself and passes what the subagent needs in task.
  • Concurrency. Each chat runs at most the configured number of subagents at once; the rest wait in a first-in, first-out queue. See Subagent settings.

get_subagent_result

Section titled “get_subagent_result”

Collect the result or current status of a subagent started by this chat.

ParameterTypeRequiredDescription
session_idstringyesThe child session id that Agent returned.

A running or queued subagent reports its status. An id from another chat, or from before a host restart, is unknown because the run registry is in memory; the error names the transcript path when it survives.

Subagent roles

Section titled “Subagent roles”

The Agent tool lists the available definitions in its description. Four are built in:

RolePurposeToolsNotes
scoutRead-only recon. Returns compressed context: paths, symbols, call sites.read, grep, find, ls, bash, spec_grep, spec_get, spec_graph, web_search, fetch_contentbash is for read-only inspection.
plannerRead-only planning. Returns an ordered, file-level change plan.read, grep, find, ls, spec_grep, spec_get, spec_graphWrites no code or files.
workerImplements a well-scoped task end to end.pi defaults: read, bash, edit, writeLeaves all changes uncommitted and never runs history- or index-changing git commands; the parent owns commits.
reviewerRead-only review of a named diff or area. Ends with Verdict: Approve or Verdict: Request changes.read, grep, find, ls, bash, spec_grep, spec_get, spec_graphAlso reads the repository’s agent guidance files (project context).

Custom agent definitions

Section titled “Custom agent definitions”

Add your own roles as Markdown files with frontmatter. The body is the system prompt.

LocationScopeLoaded when
<pi agent dir>/agents/*.md (by default ~/.pi/agent/agents/)PersonalAlways
<workspace>/.pi/agents/*.mdProjectThe project is trusted
<workspace>/.agents/agents/*.mdProjectThe project is trusted

Names resolve built-in first, then personal, then project, and the first definition with a name wins. A definition therefore cannot replace a built-in role or a personal role of the same name. Files that are malformed, or that lack a name, a description, or a body, are skipped silently. The frontmatter is read line by line as key: value, not as full YAML.

FieldRequiredDescription
nameyesRole name used as subagent_type.
descriptionyesWhat the role is for; shown to the parent agent.
toolsnoComma-separated tool names, optionally in brackets. Omitted means pi’s default tools.
modelnoPins the model. A pin cannot be overridden by the Agent call.
thinkingnoOne of off, minimal, low, medium, high, xhigh, max. Other values are ignored.
max_turnsnoPositive integer turn cap.
inherit_project_contextnotrue to load the repository’s agent guidance files.
skillsnoComma-separated skill names to load.
extensionsnotrue to give the role ThinkRail’s curated child extension set (spec read tools and web tools).

Subagent settings

Section titled “Subagent settings”

Settings → Chat → Subagents has Allow subagents (global switch, on by default) and Per chat at once (concurrency limit, 1 to 16, default 4). The active workspace can override both. Work already running always finishes when you turn subagents off. While subagents are off, Agent fails with “Subagents are disabled in this session.”

Background command tool

Section titled “Background command tool”

Provided by the pi-background-commands package. It starts a long-running, non-interactive shell command that the chat owns, without holding the agent’s turn. Ordinary bash is unchanged.

background_command

Section titled “background_command”

One tool with four actions. Each action accepts only its own parameters; extra parameters are rejected.

ParameterTypeRequiredDescription
actionstart | list | output | stopyesWhat to do.
commandstringstartThe shell command, 1 to 65,536 characters. Start only.
namestringnoDisplay name, up to 200 characters. Start only.
timeoutnumbernoTimeout in seconds. Start only. There is no default timeout.
idstringoutput, stopCommand id returned by start.

Behavior and limits:

  • At most 8 commands are active at once, and the latest 20 finished records are kept.
  • Output is a replacement snapshot of the last 2,000 lines or 50 KiB, not an archive.
  • There is no stdin and no terminal. The agent is told not to detach with &, nohup, or disown.
  • When a command finishes on its own, a background-command-completion message with a short excerpt is delivered as a follow-up and starts a turn. A command you stop does not wake the agent.
  • Stopping requests cancellation; it is not instant.
  • Records live in host memory. After a host restart, earlier ids are unavailable.

You see running and finished commands in the chat’s Resources view.

Host tools

Section titled “Host tools”

These tools are registered by the ThinkRail host rather than by a portable package. They are always present in parent chats, except request_review.

ask_user_question

Section titled “ask_user_question”

Ask you one or more structured multiple-choice questions. The chat shows them as an interactive card and the run waits for your answer.

ParameterTypeRequiredDescription
questionsarrayyesOne or more questions. Question text must be unique within a call.
questions[].questionstringyesThe full question, ending with a question mark.
questions[].headerstringyesShort chip label, up to 16 characters.
questions[].optionsarrayyes2 to 4 options with unique labels.
questions[].options[].labelstringyesOption text, up to 60 characters.
questions[].options[].descriptionstringyesWhat the option means or what it costs.
questions[].options[].previewstringnoMarkdown shown beside the option. Single-select only.
questions[].options[].recommendedReasonstringnoOne sentence, up to 160 characters, on why the agent recommends this option.
questions[].multiSelectbooleannoAllow several answers. Default: false.

Notes:

  • Every question also gets an Other free-text answer, and you can skip the whole set. The agent must not write its own “Other” option; the labels Other, Type something., Chat about this, and Next → are reserved and rejected.
  • A recommended option goes first, with “(Recommended)” in its label.
  • Replying in the chat instead of answering the card supersedes the card, and your reply arrives as the next message.
  • The call should be the only tool call in its assistant message; other calls in that message are discarded.

set_title

Section titled “set_title”

Name the chat, its workspace, and the workspace branch.

ParameterTypeRequiredDescription
chat_titlestringno3 to 6 words, in the language you write in.
workspace_namestringno2 to 5 words naming the task, in your language.
branchstringnoShort English kebab-case branch slug. Only valid together with workspace_name.

The agent calls it once, when the task is clear, passing every name still missing. A name already set, by an earlier call or by you, is kept, and the result says what was applied. A per-turn reminder appears only while a name is still missing.

resolve_comment

Section titled “resolve_comment”

Mark a review comment as resolved after addressing it.

ParameterTypeRequiredDescription
commentIdstringyesThe comment id from the review package the chat received, such as rc_1a2b3c4d.
notestringnoOne short line on what was done, shown in the review sidebar.

It is valid only for comments sent to this chat. If a comment is unclear or the agent disagrees, it replies in the conversation and does not resolve it.

request_review

Section titled “request_review”

Ask an independent, read-only reviewer subagent to review a completed plan step. The result is a verdict, approve or request_changes, with findings, plus text telling the agent what to do next under the current review policy.

ParameterTypeRequiredDescription
itemIdstringyesId of the plan step whose change set to review.

The tool is withheld unless Settings → Models → Review → Agent-triggered review is on (off by default). The Automatic fix cycle switch in the same group decides whether the next action is to fix the findings once and re-review, or to stop and report them. The reviewer model comes from Review model.

Web research tools

Section titled “Web research tools”

Provided by the third-party pi-web-access package, bundled at version 0.13.0. Search works without keys by default; optional provider keys go in ~/.pi/web-search.json. In ThinkRail the workflow parameter defaults to none, because the package’s browser curation page cannot open from the host. Video frame extraction needs ffmpeg and, for YouTube, yt-dlp on the host.

web_search

Section titled “web_search”
ParameterTypeRequiredDescription
querystringnoA single query.
queriesstring[]noSeveral queries with different angles; each gets its own answer. Preferred for research.
numResultsnumbernoResults per query. Default: 5, maximum 20.
includeContentbooleannoAlso fetch full page content in the background.
recencyFilterday | week | month | yearnoLimit results by age.
domainFilterstring[]noLimit to domains; prefix a domain with - to exclude it.
providerauto | openai | brave | parallel | tavily | exa | perplexity | gemininoSearch provider. Default: auto.
workflownone | summary-review | auto-summarynoCuration mode. ThinkRail sets none when the agent omits it.

Provide query or queries; with neither, the call returns an error.

fetch_content

Section titled “fetch_content”

Fetch URLs and extract readable Markdown. Handles web pages, PDFs, GitHub repositories, YouTube transcripts, and local video files.

ParameterTypeRequiredDescription
urlstringnoA single URL.
urlsstring[]noSeveral URLs, fetched in parallel.
forceClonebooleannoClone a large GitHub repository that exceeds the size threshold.
promptstringnoQuestion for video analysis (YouTube and video files).
timestampstringnoFrame time or range for video, such as 23:45 or 23:41-25:00.
framesintegernoNumber of video frames, 1 to 12.
modelstringnoOverride the Gemini model for video analysis.

Provide url or urls. Content is stored for later retrieval, and long single-page results are truncated inline.

get_search_content

Section titled “get_search_content”

Retrieve the full stored content from an earlier web_search or fetch_content call.

ParameterTypeRequiredDescription
responseIdstringyesThe id returned by the earlier call.
querystringnoWhich query’s content to return (search results).
queryIndexnumbernoIndex of the query.
urlstringnoWhich URL’s content to return (fetch results).
urlIndexnumbernoIndex of the URL.

Visualize tool

Section titled “Visualize tool”

Provided by the visualize extension: the portable package @thinkrail/pi-visualize, composed into ThinkRail as an extension that you can turn off in Settings → Extensions. It renders a diagram or an options comparison as a card in the chat instead of ASCII art or a Markdown table.

visualize

Section titled “visualize”
ParameterTypeRequiredDescription
typediagram | comparisonyesWhich visualization to render.
titlestringnoHeading above the visualization.
mermaidstringdiagramMermaid source of any diagram kind.
optionsarraycomparisonThe alternatives being compared.
options[].namestringyesShort label.
options[].descriptionstringnoOne or two sentences.
options[].prosstring[]noAdvantages.
options[].consstring[]noDrawbacks.
options[].recommendedbooleannoHighlights the one option the agent endorses.
options[].mermaidstringnoMermaid diagram for this option.

ThinkRail validates Mermaid syntax on the host with the same Mermaid version the browser renders. Invalid syntax is returned to the agent as a tool error so it can correct and retry. Fenced mermaid blocks in any Markdown the app renders also draw as diagrams.
